### Understanding vanity address generation

- **Tool:** Perplexity
- **Prompt used:**
  > Explain how to generate a Bitcoin mainnet Legacy P2PKH address from a secp256k1 keypair. Explain compressed public keys, SHA-256 followed by RIPEMD-160, the 0x00 version byte, the double-SHA-256 checksum, Base58 encoding, and case-insensitive vanity-prefix matching. Identify common implementation mistakes.
- **AI output/summary:** A Bitcoin mainnet Legacy P2PKH address is generated by first creating a secp256k1 keypair and extracting the 33-byte compressed public key. Hash the public key with SHA-256, then RIPEMD-160 to obtain a 20-byte public key hash.
Prepend the mainnet version byte 0x00, calculate a four-byte checksum using double SHA-256, and append the checksum. Finally, encode the result using Base58 to produce the Legacy address, which begins with 1.
For the vanity requirement, characters 2–4 of the address must match the first three letters of your first name, ignoring case. The assignment specifies extracting letters A–Z and continuing with the last name if the first name has fewer than three letters.
Common mistakes include using an uncompressed public key, reversing the hash order, calculating the checksum incorrectly, using the wrong version byte, implementing Base58 incorrectly, and performing case-sensitive prefix matching.

### P2P communication and block validation

- **Tool:** Perplexity
- **Prompt used:**
  > Help me reason through a three-node local P2P blockchain using the configured peer addresses. Explain a block-receive handler that checks (1) recomputed hash, (2) proof-of-work difficulty, (3) prev_hash against the local tip, and (4) index equals local tip index plus one. Explain how to handle offline peers without crashing and reject conflicting blocks at the same height.
- **AI output/summary:** In a three-node P2P blockchain, each node reads its peers’ addresses from its configuration file and broadcasts newly mined blocks to them using HTTP requests or TCP sockets.
When a node receives a block, it must perform four validation checks:
1. Hash verification: Recalculate the block’s SHA-256 hash and confirm it matches the received hash.
2. Difficulty verification: Ensure the hash starts with the required number of hexadecimal zeros.
3. Chain continuity: Confirm prev_hash matches the hash of the node’s current latest block.
4. Index sequence: Confirm the block’s index equals the current tip’s index plus one.
If all checks pass, the node appends the block to its local chain. If any check fails, it rejects the block. When a peer is offline or a request fails, the node should log a warning and continue operating without crashing.
The assignment uses first-valid-block-wins consensus: a node accepts the first valid block extending its current chain and rejects conflicting blocks at the same height. Simultaneous mining can therefore cause a fork, which is a known limitation of this assignment.

### Consensus and fork demonstration

- **Tool:** Perplexity
- **Prompt used:**
  > Explain first-valid-block-wins consensus for this assignment, including what happens when two nodes mine different blocks at the same height. Suggest a safe test plan to demonstrate the documented fork limitation without implementing Assignment 2's most-work chain rule.
- **AI output/summary:** First-valid-block-wins consensus means a node accepts the first valid block it receives that extends its current blockchain and rejects conflicting blocks at the same height. If two nodes mine different blocks at the same height simultaneously, each may accept its own block and reject the other node’s block because the blocks have different hashes. This creates a fork, where the nodes have different blockchain states. To demonstrate this safely, start all three nodes with difficulty 6, then trigger mining on Node 2 and Node 3 at nearly the same time. Compare their block hashes and chain states to show whether a fork occurs. Repeat if necessary, since simultaneous mining does not guarantee a fork every time. For this assignment, the fork is an expected limitation. Do not implement the most-work chain rule; that is reserved for Assignment 2.
